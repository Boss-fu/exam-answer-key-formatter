# 自動切圖訓練交接

給接手的 Claude／Codex。接手後先讀完這份和 `AGENTS.md`，再動手。

**你的角色（2026-11-05 起）：** 你是實作方，另一台電腦的 Claude 是監督方。請照下面「兩台協作」的規則做，**不要直接推 `main`**。

> **這個 repo 是公開的。** 不要把考卷、學生資料、伺服器位址、帳號密碼或 `ocr/results/` 內的東西提交進來。

## 任務

把使用者手動截圖（考卷上的圖、表）換成自動切圖。程式在 `ocr/figcrop/`。

目標（使用者原話整理）：手動截圖有瑕疵但就是可接受範圍，自動要做到同樣程度，**有文字層和純圖片（掃描）的 PDF 都要接近 95% 以上**，不可漏字、偏移、缺角、缺邊，也不可多其他的字。

目前**只做切圖**。OCR、題庫 Excel、清除筆跡都暫停，使用者沒開口就不要碰；也不要跑 `tools/night/run.sh`、`status.sh`。

## 環境

```bash
git clone https://github.com/Boss-fu/exam-answer-key-formatter.git
cd exam-answer-key-formatter && bash ocr/setup_env.sh
```

`setup_env.sh` 會建 `~/.venvs/zizi-exam`（Python 3.11）和下載 OCR 模型；最後的測試卷步驟是 OCR 用的，切圖不需要，失敗也沒關係。版面模型 `rapid-layout` 第一次跑 `crop.py` 會自動裝。

## 不在 git 裡、要另外準備

1. **訓練資料夾**（手動截圖標準答案）：向使用者要 `自動切圖訓練資料`，放到 `~/Desktop/待匯入/自動切圖訓練資料`，或跑評測前設 `FIGCROP_SRC=<路徑>`。每份卷是 PDF 加圖表素材 ZIP，使用者會持續丟新卷。
2. **基準 `baseline.json`**：不用複製，自己重建，順便驗證環境：
   ```bash
   ocr/figcrop/run_eval.sh base
   ```
   同一批資料、同一版程式應該接近上表的 95.8%（`manual: 192`）。差很多就是環境或資料不對，**先查清楚再改程式**。確認後：
   ```bash
   cp ocr/results/figcrop_runs/base/gt_eval.json ocr/results/figcrop_gt/baseline.json
   ```
3. **新卷**：向使用者要考卷資料夾。第一批 12 份清單在下面。

## 工作流程

每一輪只改一件事，改完：

```bash
ocr/figcrop/run_eval.sh <標籤>
```

會跑單元測試、評測、閘門（`tools/night/gate_figcrop.py`）和逐張比較（`compare_eval.py`）。一輪約 5～50 分鐘，機器忙或用電池時會很慢。

閘門通過（召回、IoU、題號都不降，多框不增，且至少一項變好）**還不夠**，也要看新卷（見下節）。兩邊都沒問題才：

1. 只 `git add` 自己改的檔案。commit 訊息用繁中，寫清楚數字。
2. `git pull --rebase --autostash` 再 `git push`，都在 `figcrop-worker`，不要推 `main`。
3. `cp` 新結果覆蓋 `baseline.json`，再到 PR 留言回報。

### 新卷檢查（AGY／Gemini 當檢查員）

```bash
~/.venvs/zizi-exam/bin/python ocr/figcrop/wild_run.py crop <pdf>   # 每份卷跑一次
~/.venvs/zizi-exam/bin/python ocr/figcrop/wild_run.py review       # 逐頁請 agy 判，已判過的跳過
~/.venvs/zizi-exam/bin/python ocr/figcrop/wild_run.py report
```

結果在 `ocr/results/figcrop_wild`。重跑前先把舊資料夾改名留著比對。

- **AGY 只是第二意見。** 框完全沒變時，它也有約 6% 的判定會翻轉，所以幾個百分點的升降不算數。**要逐框比對：只看真的有變的框是變好還是變差。**
- 抽查過，它抓到的問題大多是真的，而且抓到過閘門漏掉的副作用（修剪把表格表頭切掉，手動卷剛好沒這種情況）。
- **使用者沒有 AGY 的話**：改用自己的 Claude 看 `pages/p*.jpg`，但先問過使用者。

## 使用者定的規則

- 一律繁體中文回覆。
- 每輪結果要贏過前一輪，不要亂試。過不了閘門就查原因，**不可為了過關放寬閘門**。
- **圖說**（`圖(五)`、`表一`）框或不框都算合格，因為手動本身兩種都有；切圖輸出保留圖說，評測取高分，嚴格分記在 `recall_strict`。
- 最終產品執行時不可用生成式 AI。本機版面模型可以（和 OCR 同等級）。AGY 只用在開發時檢查。
- 不可把學生資料放進 git。
- **送圖給 AGY 前要遮姓名**：`wild_run.py` 會遮姓名座號列；優先用 `_空白`／`_blank` 版。送出去就撤不回。第一批曾有未遮的頁面送出，使用者已知道。
- 資料夾沒新卷時，自己從考卷資料夾挑沒用過的卷來驗證，不用等。
- 使用者要看到結果就給結果，不要等人驗收；能做的先做。回報要誠實，沒達標就說沒達標。
- 額度快用完（≥97%）就停，不要用 extra usage。

## 程式結構

`crop.py` 的 `crop_items(img)` 是整頁入口：判方向轉正 → 版面模型（PP-DocLayout v3）加備援候選 → 逐框精修 → 合併 → 過濾 → 猜題號 → 座標換回原頁。`--json` 輸出的 page／x／y／w／h／qno／png 是 `local-app/server.js` 和網頁在讀的，**不要改欄位**。

| 檔案 | 用途 |
|---|---|
| `crop.py` | 流程、合併、過濾、`guess_qno` |
| `refine.py` | 單框精修、`text_like`（像題目句子的判斷） |
| `gt_eval.py` | 比對手動圖（SIFT 定位） |
| `sync_gt.py` | 訓練資料夾 → `ocr/results/figcrop_gt`。**會覆蓋 exam.pdf，評測跑到一半不要執行** |
| `wild_run.py` | 新卷切圖加 AGY 檢查 |
| `review_sheet.py` | 手動／自動對照頁，給人驗收 |
| `test_refine.py` | 單元測試：`python -m unittest ocr.figcrop.test_refine` |

**學到的事**（都踩過）：
- 版面模型的框其實很準，掃描卷也是。多數錯誤來自後面的擴張和合併，所以要信任模型框、只小幅外擴。
- 短 OCR 行要小心：`(`、`象。`、`44~47題`、`背面還有題目` 都曾被當成圖的標籤把框撐大。
- 只擦到邊的句子不能拿來切圖，要看實質重疊或行中心。
- 表格的列也像句子，修剪類規則要避開表格。
- 放寬面板間距（4.5%→5.5% 頁寬）會把左右欄的圖併起來，不要再試。
- 手動框也有瑕疵（崇林 Q39 多框選項文字、崇林 p5 框整段文章），不要追著它調。

## 兩台協作

### 分工

| | 實作方（接手的這台） | 監督方（原本的電腦） |
|---|---|---|
| 改切圖程式 | ✅ 只在分支 `figcrop-worker` | ❌ 不改 |
| 推 `main` | ❌ 不推 | 使用者同意後才合併 |
| 評測 | 跑手動評測、調規則用的 8 份新卷 | 用同一批資料獨立重跑，加上保留的 4 份 |
| 派工 | 照 PR 裡的指示做 | 在 PR 留言派下一項 |

**推上 `main` 後主機 5 分鐘內就會自動更新，所以合併一定要使用者同意。**

### 開工步驟

```bash
git checkout -b figcrop-worker origin/main
git push -u origin figcrop-worker
gh pr create --draft --base main --title "切圖訓練（實作方）" --body "實作方工作紀錄，請監督方在此留言派工。"
```

已有這個分支就 `git fetch origin` 後切過去，不要重開。之後都在同一個 PR 溝通。

### 溝通方式：同一個 draft PR

兩邊的 Claude 帳號不同，不能直接傳訊息，所以用 PR 留言。**repo 是公開的，留言任何人都看得到：不可貼考卷內容、學生資料、截圖、伺服器位址或帳密**，只貼卷名、題號、座標、分數。

實作方每輪：

1. **開工前**讀最新留言，監督方的指示優先：
   ```bash
   gh pr view figcrop-worker --comments
   ```
2. 一輪只改一件事，跑 `ocr/figcrop/run_eval.sh <標籤>`。閘門通過就 commit 並 push 到 `figcrop-worker`；**沒過也要回報**，不要放寬閘門。
3. 留言回報，固定格式：
   ```
   【實作回報】commit: <短 hash 或「未提交」>
   改了什麼：<一句>
   閘門：<PASS/FAIL 那一行原文>
   逐張：<compare_eval 的 進／退／題號對→錯，沒有就寫無>
   新卷：<有變的框，變好/變差；沒跑就寫沒跑>
   下一步：<一句>
   ```
4. 沒有人在等也要繼續下一項。用 Monitor 工具每分鐘看 PR 有沒有【監督】新留言，閒置時不耗額度（Monitor 最長 30 分鐘，到期要重開）；沒有 Monitor 才改成定時檢查：
   ```bash
   last=-1; while true; do n=$(gh pr view figcrop-worker --json comments --jq '[.comments[]|select(.body|startswith("【監督】"))]|length' 2>/dev/null); [ -n "$n" ] && [ "$last" -ge 0 ] && [ "$n" -gt "$last" ] && echo "監督方有新留言"; [ -n "$n" ] && last=$n; sleep 60; done
   ```

監督方會在留言開頭寫【監督】，內容可能是：下一項任務、要修正的問題、或獨立重跑的結果。**兩邊數字對不上時，先停下來查環境，不要繼續改。**

### 基準

`baseline.json` 不在 git。實作方用自己機器上的結果更新自己的基準；只有閘門通過且 push 之後才更新。

### 任務順序

1. **先把評測加速（最優先）**：現在一輪 5～50 分鐘，幾乎都花在重跑 OCR 和版面模型，但調規則時這些結果根本沒變。在 `gt_eval.py` 和 `wild_run.py` 的評測流程加磁碟快取：`page_rotation`、`text_lines`、`detect`、`figure_candidates` 的結果依頁面內容的雜湊存在 `ocr/results/figcrop_cache`（不進 git），`--no-cache` 可關閉。
   - **正式切圖流程（`--json`、server）不可用快取，也不可改變輸出。**
   - 驗收：有快取和沒快取跑出來的 `gt_eval.json` 除了時間之外要完全相同，閘門要 PASS 或數字不變；回報前後秒數。
2. 「接下來」的第 1 項：框上緣擦到半行題幹。只用調規則的 8 份找問題。

`local-app/server.js` 等其他檔案可能有不屬於切圖的未提交改動，不要順手提交或丟棄。
